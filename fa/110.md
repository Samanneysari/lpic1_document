## 110.1 — ممیزی حساب، port و sudo

### مفهوم و کاربرد

امنیت یعنی موجودی، کم‌کردن سطح حمله، احراز هویت، مجوز حداقلی، update، log و recovery. SUID باعث اجرای binary با effective UID مالک و SGID روی binary با گروه فایل می‌شود؛ وجودشان خودکار نشانهٔ بدافزار نیست ولی باید توجیه شوند.

port باز را از دو نگاه می‌بینیم: ss روی host و nmap از دید scanner. scan فقط هدفی که مجوز دارید. sudo فرمان محدود طبق policy اجرا و ثبت می‌کند؛ su هویت/session را عوض می‌کند.

### مثال 1: ممیزی خواندنی host

خروجی می‌تواند زیاد باشد.

```bash
sudo find / -xdev -type f \( -perm -4000 -o -perm -2000 \) -print
sudo ss -lntup
who
w
last -a | head
```

**توضیح خط‌به‌خط:**

1. از root همین filesystem؛ فایل عادی؛ پرانتز دو شرط OR؛ SUID یا SGID.
2. listenerهای local و پردازه را می‌بیند.
3. نشست‌های اکنون.
4. نشست، فعالیت و load.
5. تاریخچهٔ login از دادهٔ موجود و host در انتهای خط.

**نتیجه و بررسی:** هر یافته را با package owner، expected baseline و change record مقایسه کنید. نبود تاریخچه می‌تواند از rotation/پاک‌شدن باشد.

### مثال 2: scan محدود loopback

فقط خود VM.

```bash
sudo nmap -sT -sV 127.0.0.1
sudo lsof -nP -i
sudo fuser -n tcp 22
```

**توضیح خط‌به‌خط:**

1. sT connect scan و sV تشخیص نسخه روی loopback است.
2. socketهای process؛ n و P تبدیل نام/port را خاموش می‌کنند.
3. PIDهای استفاده‌کنندهٔ TCP port 22 را می‌یابد.

**نتیجه و بررسی:** scan loopback دسترسی از بیرون را ثابت نمی‌کند؛ bind address، route و firewall فرق دارد.

### مثال 3: sudo محدود و limit

بدون ویرایش policy ابتدا وضعیت را بخوانید.

```bash
sudo -l
ulimit -a
ulimit -n
sudo visudo -cf /etc/sudoers
```

**توضیح خط‌به‌خط:**

1. فرمان‌های مجاز کاربر فعلی را فهرست می‌کند.
2. limitهای shell فعلی را می‌خواند.
3. حد file descriptorهای باز را می‌خواند.
4. c check و f فایل اصلی؛ policy را ویرایش نمی‌کند.

**نتیجه و بررسی:** PAM limits در `/etc/security/limits.conf` و limits.d برای loginهاست؛ serviceهای systemd ممکن است `LimitNOFILE=` جدا داشته باشند.

### اشتباه رایج و عیب‌یابی

هرگز برای راحتی `%group ALL=(ALL) NOPASSWD: ALL` نگذارید. wildcard و editorهای مجاز ممکن است shell/فایل دلخواه باز کنند.

### نکته‌های تکمیلی این سرفصل

برای aging: `passwd USER` رمز تعاملی، `chage -l USER` مشاهده، `chage -m 1 -M 90 -W 14 USER` حداقل/حداکثر/هشدار و `passwd -S USER` status است. `/etc/shadow` hash است نه plaintext و نباید کپی عمومی شود. `lastlog` آخرین login هر حساب را می‌خواند.

نمونهٔ sudoers محدود: `%webops ALL=(root) /usr/bin/systemctl reload nginx.service`. webops گروه، ALL میزبان، root هویت اجرا و بقیه فرمان دقیق است. آن را با `visudo -f /etc/sudoers.d/webops` بسازید، mode 0440 و `visudo -cf` بررسی کنید. حتی systemctl مجاز را از نظر امکان تغییر unit و privilege escalation ارزیابی کنید. `sudo -u www-data id` یک فرمان را با هویت مشخص؛ `su - alice` محیط login-like و `su alice` محیط حفظ‌شده‌تر می‌سازد.

## 110.2 — کم‌کردن سطح حمله

### مفهوم و کاربرد

service لازم نیست نباید اجرا یا گوش کند. `disable` راه enable شدن در boot را برمی‌دارد ولی service جاری را stop نمی‌کند و socket می‌تواند دوباره آن را فعال کند. `mask` activation معمول را مسدودتر می‌کند و وابستگی را هم ممکن است بشکند.

قفل password همهٔ روش‌های ورود را نمی‌بندد. `/etc/nologin` برنامه‌های login همکار را برای کاربران غیرroot محدود می‌کند؛ service account می‌تواند nologin shell داشته باشد.

### مثال 1: موجودی exposure

بدون تغییر.

```bash
systemctl --type=service --state=running
systemctl list-sockets --all
sudo ss -lntup
systemctl cat sshd.service
```

**توضیح خط‌به‌خط:**

1. serviceهای درحال اجرا را می‌خواند.
2. socket unitهای فعال/غیرفعال را می‌خواند.
3. listener و bind address را می‌خواند.
4. unit و overrideهای SSH را در RPM می‌خواند؛ در Debian نام ssh.service است.

**نتیجه و بررسی:** listener روی 127.0.0.1 با 0.0.0.0 فرق دارد. service بدون port ممکن است همچنان مهم/آسیب‌پذیر باشد.

### مثال 2: چرخهٔ service آزمایش

نام واقعی harmless lab service را استفاده کنید؛ روی SSH یا شبکه انجام ندهید.

```bash
systemctl status example.service --no-pager
sudo systemctl disable --now example.service
systemctl is-enabled example.service
systemctl is-active example.service
systemctl list-sockets --all | grep example
```

**توضیح خط‌به‌خط:**

1. وضعیت، آخرین log و مسیر unit را می‌خواند.
2. disable boot activation و now توقف فعلی؛ قبلش وابستگی را بررسی کنید.
3. وضعیت enable را بررسی می‌کند.
4. وضعیت اجرا را جدا بررسی می‌کند.
5. socket activation مرتبط را می‌جوید.

**نتیجه و بررسی:** برای بازگشت در lab `sudo systemctl enable --now example.service` فقط اگر وضعیت اولیه enabled+active بوده است. نام example واقعی نیست و نباید عیناً اجرا شود.

### مثال 3: مکانیزم‌های قدیمی

فقط خواندن.

```bash
ls /etc/xinetd.d 2>/dev/null
test -f /etc/hosts.allow && cat /etc/hosts.allow
test -f /etc/hosts.deny && cat /etc/hosts.deny
ls /etc/init.d
```

**توضیح خط‌به‌خط:**

1. تعریف serviceهای xinetd را اگر نصب است می‌بیند.
2. قواعد TCP wrapper قدیمی را اگر هست می‌خواند.
3. فایل deny قدیمی را می‌خواند.
4. scriptهای SysV/compatibility را فهرست می‌کند.

**نتیجه و بررسی:** hosts.allow/deny فقط برنامهٔ ساخته‌شده با پشتیبانی TCP wrappers را کنترل می‌کند؛ firewall عمومی نیست.

### اشتباه رایج و عیب‌یابی

SSH را از راه همان SSH stop یا mask نکنید. ابتدا console و نشست دوم و rollback. سرویس ناشناخته را صرفاً به‌خاطر نام disable نکنید؛ dependency و مالک بسته را ببینید.

### نکته‌های تکمیلی این سرفصل

`/etc/passwd` معمولاً x و shadow hash را دارد. FTP/Telnet/r-services قدیمی را اگر نیاز نیست حذف/محدود و جای امن را استفاده کنید. update از مخزن signed، حذف بستهٔ بدون پشتیبانی، reboot لازم پس از kernel و backup خارج host با تست restore بخش امنیت است. firewall و تنظیم خود service را در کنار bind address ببینید.

## 110.3 — هویت SSH، tunnel و رمزنگاری GPG

### مفهوم و کاربرد

در SSH، host key هویت server و key کاربر هویت client را پشتیبانی می‌کند. private key هرگز ارسال نمی‌شود؛ public key در `authorized_keys` سرور قرار می‌گیرد. `known_hosts` کلید host دیده‌شده را نگه می‌دارد و تغییر ناگهانی را هشدار می‌دهد؛ پذیرش اول باید پس از مقایسهٔ fingerprint از کانال مطمئن باشد.

Encryption محرمانگی و signature صحت/استفاده از private key امضاکننده را می‌دهد. signature بدون اثبات مالکیت public key کافی نیست.

### مثال 1: کلید SSH مصرفی

در حساب lab؛ اگر فایل مقصد هست نام تازه انتخاب می‌کنیم.

```bash
ssh-keygen -t ed25519 -a 100 -f "$HOME/.ssh/id_ed25519_lpic" -C "lpic-lab"
ssh-keygen -lf "$HOME/.ssh/id_ed25519_lpic.pub"
eval "$(ssh-agent -s)"
ssh-add "$HOME/.ssh/id_ed25519_lpic"
ssh-add -l
```

**توضیح خط‌به‌خط:**

1. t نوع، a دورهای KDF فایل private، f مسیر یکتا و C برچسب است؛ passphrase قوی وارد کنید.
2. fingerprint public key را می‌خواند.
3. خروجی agent را در shell فعلی ارزیابی و متغیرهای اتصال را تنظیم می‌کند.
4. پس از passphrase کلید private را داخل agent می‌گذارد.
5. fingerprint کلیدهای agent را می‌خواند.

**نتیجه و بررسی:** فایل بدون .pub خصوصی است؛ نمایش/commit نشود. برای cleanup ابتدا `ssh-add -d PATH` و بعد agent را با `ssh-agent -k` ببندید؛ فایل‌های آزمایش را فقط با تصمیم خود حذف کنید.

### مثال 2: config و اتصال

سرور مجاز lab با fingerprint از console.

```sshconfig
Host lpic-web
    HostName server.example.net
    User alice
    IdentityFile ~/.ssh/id_ed25519_lpic
    IdentitiesOnly yes
chmod 700 ~/.ssh
chmod 600 ~/.ssh/config ~/.ssh/id_ed25519_lpic
chmod 644 ~/.ssh/id_ed25519_lpic.pub
ssh lpic-web
```

**توضیح خط‌به‌خط:**

1. block در ~/.ssh/config؛ alias، نام واقعی، user، key و محدودکردن هویت‌ها. example.net placeholder است.
2. فقط مالک به directory دسترسی دارد.
3. تنظیم و private key فقط مالک.
4. public key قابل خواندن است.
5. alias config را استفاده می‌کند؛ fingerprint را با کانال مطمئن مقایسه کنید.

**نتیجه و بررسی:** `ssh-copy-id -i ~/.ssh/id_ed25519_lpic.pub alice@REAL_HOST` فقط public key را پس از احراز هویت نصب می‌کند. قبل از بستن نشست فعلی، نشست دوم را آزمایش کنید.

### مثال 3: سه tunnel

فقط مقصد مجاز و bind loopback.

```bash
ssh -N -L 127.0.0.1:15432:db.internal:5432 alice@gateway.example.net
ssh -N -R 127.0.0.1:18080:localhost:8080 alice@gateway.example.net
ssh -N -D 127.0.0.1:1080 alice@gateway.example.net
```

**توضیح خط‌به‌خط:**

1. N بدون فرمان remote؛ L listener محلی 15432، از gateway به db:5432.
2. R listener سمت remote روی loopback و مسیر به localhost:8080 سمت client.
3. D SOCKS proxy محلی روی loopback.

**نتیجه و بررسی:** هرکدام foreground می‌ماند و با Ctrl+C تمام می‌شود. معنی localhost در -R سمت client مقصد مهم است؛ policy server می‌تواند forwarding را منع کند.

### مثال 4: GPG round trip

home آزمایش و هویت ساختگی خودتان؛ passphrase و revocation را محافظت کنید.

```bash
gpg --full-generate-key
gpg --list-keys
gpg --armor --output public.asc --export USER_ID
gpg --output revoke.asc --gen-revoke USER_ID
gpg --encrypt --recipient USER_ID --output secret.txt.gpg secret.txt
gpg --decrypt --output restored.txt secret.txt.gpg
gpg --armor --detach-sign secret.txt
gpg --verify secret.txt.asc secret.txt
```

**توضیح خط‌به‌خط:**

1. تعاملی key pair می‌سازد؛ نوع/انقضا/هویت و passphrase را انتخاب می‌کنید.
2. public keyها را می‌خواند.
3. public key را ASCII-armored صادر می‌کند؛ USER_ID واقعی lab.
4. گواهی لغو می‌سازد؛ جدا و امن نگه دارید.
5. برای گیرنده رمز می‌کند.
6. با private key باز می‌کند.
7. امضای جدا secret.txt.asc می‌سازد.
8. تطابق امضا را بررسی می‌کند.

**نتیجه و بررسی:** با cmp secret.txt restored.txt round trip را بررسی کنید. Valid signature فقط تعلق cryptographic به key را می‌گوید؛ trust هویت جداست.

### اشتباه رایج و عیب‌یابی

هشدار host key را با حذف کورکورانهٔ known_hosts خاموش نکنید؛ احتمال reinstall مشروع و حمله را تفکیک کنید. private key را chmod 644 نکنید. DSA قدیمی است و نباید ساخته شود.

### نکته‌های تکمیلی این سرفصل

نام‌های تاریخی user key: id_rsa، id_dsa، id_ecdsa، id_ed25519 و .pubهایشان؛ host keyهای server زیر `/etc/ssh/ssh_host_*`. DSA را فقط برای شناخت آزمون بدانید. فایل system-wide client trust معمولاً `/etc/ssh/ssh_known_hosts` است.

برای server: `sudo sshd -t` syntax و `sudo sshd -T` تنظیم مؤثر را می‌خواند؛ پس از موفقیت `systemctl reload sshd` یا ssh مطابق توزیع. restart می‌تواند نشست تازه را خراب کند؛ نشست فعلی و console را نگه دارید. X11 tunnel با `ssh -X` و trusted `-Y` است. GPG state در `~/.gnupg` و gpg-agent cache عملیات private است؛ backup و permission را محافظت کنید.
