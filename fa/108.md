## 108.1 — ساعت سیستم، RTC و NTP

### مفهوم و کاربرد

System clock را kernel هنگام اجرا نگه می‌دارد؛ RTC ساعت سخت‌افزاری است و timezone روش نمایش. سرورها معمولاً RTC را UTC نگه می‌دارند. NTP با چند منبع offset و delay را تخمین می‌زند؛ UDP 123 رایج است. Chrony در شبکه‌های متغیر و VMها رایج است؛ ntpd پیاده‌سازی سنتی است.

### مثال 1: خواندن چهار وضعیت

بدون تغییر ساعت.

```bash
date --iso-8601=seconds
timedatectl status
sudo hwclock --show
readlink -f /etc/localtime
```

**توضیح خط‌به‌خط:**

1. زمان سیستم با offset را نشان می‌دهد.
2. timezone، UTC، RTC و همگام‌سازی را خلاصه می‌کند.
3. زمان RTC را می‌خواند؛ در VM ممکن است device در دسترس نباشد.
4. zone انتخاب‌شده را می‌خواند.

**نتیجه و بررسی:** اختلاف نمایش local و UTC طبیعی است؛ اختلاف لحظه‌ای بزرگ یا NTP unsynchronized نیاز به بررسی دارد.

### مثال 2: Chrony

روی سیستم دارای chronyd.

```bash
chronyc tracking
chronyc sources -v
systemctl status chronyd.service --no-pager
```

**توضیح خط‌به‌خط:**

1. offset، مرجع، stratum و وضعیت کلی را می‌خواند.
2. منبع‌ها و علامت انتخاب را نشان می‌دهد.
3. نام رایج RPM؛ در Debian ممکن است chrony.service باشد.

**نتیجه و بررسی:** علامت `^*` معمولاً منبع انتخاب‌شده است، `^+` نامزد مناسب. ستون LastRx و Reach را باهم بخوانید؛ یک نمونهٔ اولیه کافی نیست.

### مثال 3: خواندن پیکربندی

فایل را تغییر نمی‌دهیم.

```bash
grep -Ev '^[[:space:]]*(#|$)' /etc/chrony.conf
ntpq -p
```

**توضیح خط‌به‌خط:**

1. comment و خط خالی را حذف می‌کند؛ مسیر Debian ممکن است `/etc/chrony/chrony.conf` باشد.
2. روی سیستم ntpd سنتی peerها را می‌خواند؛ نبود فرمان وقتی chrony نصب است طبیعی است.

**نتیجه و بررسی:** `pool pool.ntp.org iburst` چند آدرس pool و نمونه‌گیری سریع اولیه را می‌خواهد. `makestep 1.0 3` اجازهٔ step بزرگ در سه update اول را می‌دهد و `rtcsync` همگامی RTC از kernel را درخواست می‌کند.

### اشتباه رایج و عیب‌یابی

زمان را برای رفع علامت TLS عقب‌وجلو نکنید. ابتدا منبع، DNS، UDP 123، firewall و status daemon را بررسی کنید. step زمان در سیستم تولیدی اثر جانبی دارد.

### نکته‌های تکمیلی این سرفصل

`sudo hwclock --systohc --utc` ساعت سیستم را به RTC با تفسیر UTC می‌نویسد؛ فقط وقتی مدل RTC و زمان سیستم درست‌اند. `ntpdate` همگامی یک‌بارهٔ قدیمی و در بسیاری توزیع‌ها deprecated است. فایل ntpd معمولاً `/etc/ntp.conf` است. سرویس NTP باز و بدون کنترل را روی اینترنت منتشر نکنید.

## 108.2 — از پیام تا journal و logrotate

### مفهوم و کاربرد

Log مدرک رویداد است. Syslog facility منبع مثل auth/daemon/local0 و severity اهمیت از emerg=0 تا debug=7 است. selector `*.warning` معمولاً warning و مهم‌ترها را می‌گیرد. journald دادهٔ ساختاریافته دارد؛ rsyslog می‌تواند آن را به فایل یا سرور بفرستد.

گزارش فقط وقتی مفید است که ساعت درست، ظرفیت/retention و دسترسی مناسب داشته باشد. حذف log یک عمل برگشت‌ناپذیر و مسئلهٔ امنیتی است.

### مثال 1: پیام برچسب‌دار

بدون تغییر تنظیم.

```bash
logger -p local0.notice -t lpic-lab "test message"
journalctl -t lpic-lab --since "5 minutes ago" --no-pager
journalctl -b -p warning --no-pager -n 20
```

**توضیح خط‌به‌خط:**

1. p facility.severity، t tag و متن پیام است.
2. با tag و بازهٔ زمان همان پیام را می‌جوید.
3. همین boot، warning و مهم‌تر، آخرین 20 نتیجه.

**نتیجه و بررسی:** نبود پیام ممکن است از journald/socket یا permission باشد؛ با status سرویس و `journalctl --since` بررسی کنید.

### مثال 2: قانون rsyslog آزمایش

فقط VM؛ فایل drop-in جدید می‌سازیم و در پایان پاک می‌کنیم.

```text
local0.*    /var/log/lpic-lab.log
sudo rsyslogd -N1
sudo systemctl reload rsyslog
logger -p local0.info -t lpic-lab "file route"
sudo tail -n 5 /var/log/lpic-lab.log
```

**توضیح خط‌به‌خط:**

1. محتوای `/etc/rsyslog.d/30-lpic-lab.conf`: همهٔ severityهای local0 به فایل.
2. N1 نحو کل تنظیم را بدون شروع daemon اعتبارسنجی می‌کند.
3. بازخوانی تنظیم بدون restart کامل؛ فقط پس از موفقیت اعتبارسنجی.
4. پیام تازه برای آزمون مسیر.
5. آخر فایل مقصد را می‌خواند.

**نتیجه و بررسی:** پس از تمرین فقط drop-in و log مربوط به lab را حذف و reload کنید. نام سرویس ممکن است rsyslog.service باشد.

### مثال 3: سیاست rotation

فایل `/etc/logrotate.d/lpic-lab` در VM.

```text
/var/log/lpic-lab.log {
    weekly
    rotate 4
    compress
    missingok
    notifempty
    create 0640 root adm
}
sudo logrotate --debug /etc/logrotate.conf
```

**توضیح خط‌به‌خط:**

1. مسیر فایل و شروع block.
2. چرخش هفتگی.
3. چهار نسخهٔ قدیمی نگه داشته می‌شود.
4. نسخه‌های قدیمی فشرده می‌شوند.
5. نبود فایل خطای سخت نیست.
6. فایل خالی نمی‌چرخد.
7. فایل تازه با mode و مالک/گروه مشخص؛ گروه در توزیع باید موجود باشد.
8. پایان block.
9. کل policy را تحلیل می‌کند و rotation واقعی انجام نمی‌دهد.

**نتیجه و بررسی:** debug باید خطای syntax ندهد. `--force` تغییر واقعی می‌دهد و فقط روی log مصرفی با برنامهٔ بازکنندهٔ درست آزمایش شود.

### اشتباه رایج و عیب‌یابی

`journalctl --vacuum-time=30d` دادهٔ آرشیوی را حذف می‌کند؛ بدون سیاست retention اجرا نکنید. `copytruncate` بازهٔ از‌دست‌رفتن داده دارد.

### نکته‌های تکمیلی این سرفصل

فیلترها: `journalctl -u sshd.service` واحد، `--since/--until` زمان، `-f` دنبال‌کردن و `--disk-usage` ظرفیت است. `printf 'event\n' | systemd-cat -t lpic-lab -p info` stdin را وارد journal می‌کند. برای journal بازیابی‌شده `journalctl --directory=/mnt/recovery/var/log/journal` استفاده می‌شود.

drop-in `/etc/systemd/journald.conf.d/10-retention.conf` با `[Journal]`, `Storage=persistent`, `SystemMaxUse=500M` تنظیم نمونه است؛ قبل از restart syntax/path و فضای دیسک را بررسی کنید. مسیر اصلی `/etc/systemd/journald.conf` است. Forward قدیمی rsyslog: `*.* @192.0.2.20:514` UDP و `@@` TCP؛ برای تولید TLS احراز‌شده، queue و firewall محدود لازم است. Collector باید input را صریح فعال کند. فایل‌های رایج Debian شامل syslog/auth.log و RPM شامل messages/secure است. syslog-ng جایگزین ممکن است باشد.

## 108.3 — ایمیل محلی و صف MTA

### مفهوم و کاربرد

MUA پیام را می‌نویسد؛ MTA مثل Postfix/Sendmail/Exim انتقال و صف را مدیریت می‌کند. LPIC-1 تنظیم کامل mail server نمی‌خواهد، اما alias و forwarding محلی را می‌خواهد. موفق‌شدن فرمان mail تحویل نهایی را ثابت نمی‌کند؛ صف و log مهم‌اند.

### مثال 1: دیدن صف و برنامه

بدون ارسال خارجی.

```bash
command -v sendmail mailq mail
mailq
sendmail -bp
```

**توضیح خط‌به‌خط:**

1. وجود لایهٔ سازگار و client را بررسی می‌کند.
2. صف MTA را می‌خواند؛ empty یعنی پیام معوق ندارد.
3. روش سازگار دیگری برای دیدن صف است؛ ممکن است همان backend باشد.

**نتیجه و بررسی:** اگر commandها نیستند MTA/client نصب نشده است؛ نصب کورکورانه روی سرور تولیدی نکنید.

### مثال 2: alias محلی

این نمونه را ابتدا فقط تحلیل کنید؛ مقصد خارجی نمونه است.

```text
postmaster: root
root: admin@example.net
sudo newaliases
```

**توضیح خط‌به‌خط:**

1. در `/etc/aliases` پیام postmaster به root می‌رود.
2. پیام root به نشانی مدیریت می‌رود؛ امکان نشت و loop را بررسی کنید.
3. پس از ویرایش معتبر پایگاه alias را بازسازی می‌کند.

**نتیجه و بررسی:** قبل از تغییر، فایل را backup و مقصد را تأیید کنید. خطای newaliases باید پیش از آزمون ارسال رفع شود.

### مثال 3: آزمون محلی

فقط روی VM دارای MTA محلی.

```bash
printf "LPIC test body
" | mail -s "LPIC test" root
mailq
journalctl --since "5 minutes ago" --no-pager | grep -Ei "postfix|sendmail|exim"
```

**توضیح خط‌به‌خط:**

1. بدنه با pipe، s موضوع و root گیرندهٔ محلی است.
2. بلافاصله صف انتقال را می‌خواند.
3. log مربوط به MTA نصب‌شده را جست‌وجو می‌کند.

**نتیجه و بررسی:** صف خالی می‌تواند تحویل محلی موفق یا رد سریع باشد؛ log و mailbox محلی را هم بررسی کنید.

### اشتباه رایج و عیب‌یابی

رمز SMTP را در command line یا .forward نگذارید. forwarding خودکار می‌تواند دادهٔ حساس سیستم را بیرون ببرد.

## 108.4 — CUPS، چاپگر و صف چاپ

### مفهوم و کاربرد

CUPS job را در queue نگه می‌دارد، filter آن را آماده و backend به چاپگر می‌فرستد. Printer فیزیکی با queue منطقی یک چیز نیست. IPP پروتکل چاپ مدرن است؛ CUPS ممکن است روی TCP 631 گوش دهد. interface وب بدون policy نباید عمومی شود.

### مثال 1: وضعیت چاپ

فقط خواندن.

```bash
lpstat -t
lpstat -p -d
systemctl status cups.service --no-pager
ss -ltn | grep ":631"
```

**توضیح خط‌به‌خط:**

1. خلاصهٔ scheduler، مقصد پیش‌فرض، printer و jobها.
2. وضعیت printerها و default destination.
3. وضعیت scheduler؛ نام روی بعضی سیستم‌ها cups.
4. socket TCP گوش‌دهنده روی پورت 631 را می‌جوید؛ نبود آن ممکن است به bind محلی/عدم اجرا مربوط باشد.

**نتیجه و بررسی:** نداشتن printer در VM طبیعی است. status سرویس، صف و ارتباط دستگاه سه لایهٔ متفاوت‌اند.

### مثال 2: ارسال و پیگیری

فقط وقتی یک queue آزمایش واقعی به نام lab-printer دارید.

```bash
lp -d lab-printer document.pdf
lpq -P lab-printer
lpstat -W not-completed -o lab-printer
cancel JOB_ID
lprm JOB_ID
```

**توضیح خط‌به‌خط:**

1. d مقصد queue است و فایل job می‌شود؛ وجود فایل و مجازبودن نوع را بررسی کنید.
2. رابط سازگار LPD صف printer را می‌خواند.
3. jobهای تکمیل‌نشدهٔ queue را می‌خواند.
4. job مجاز را با شناسهٔ واقعی لغو می‌کند؛ printer را حذف نمی‌کند.
5. روش سازگار دیگر برای حذف job است.

**نتیجه و بررسی:** شناسه شبیه lab-printer-12 را از خروجی بگیرید. پاک‌کردن job کاغذی که قبلاً چاپ شده را برنمی‌گرداند.

### مثال 3: ساخت queue آزمایش

فقط URI چاپگر مجاز واقعی.

```bash
sudo lpadmin -p lab-printer -E -v ipp://printer.example.net/ipp/print -m everywhere
lpstat -p lab-printer -l
sudo lpadmin -x lab-printer
```

**توضیح خط‌به‌خط:**

1. p نام queue، E فعال‌سازی، v URI و m everywhere driverless IPP است.
2. وضعیت و جزئیات را می‌خواند.
3. x فقط queue نام‌برده را حذف می‌کند.

**نتیجه و بررسی:** example.net چاپگر واقعی نیست؛ URI مجاز را جایگزین کنید. printer قدیمی ممکن است PPD/model دیگری لازم داشته باشد.

### اشتباه رایج و عیب‌یابی

اگر job متوقف است اول پیام queue و `journalctl -u cups`، سپس DNS/route/port و وضعیت خود دستگاه را بررسی کنید. چندبار ارسال مجدد می‌تواند چاپ تکراری بسازد.

### نکته‌های تکمیلی این سرفصل

تنظیم‌ها زیر `/etc/cups` و فایل اصلی scheduler معمولاً cupsd.conf است. printers.conf را معمولاً با ابزار CUPS مدیریت می‌کنیم. `lpoptions -d NAME` مقصد پیش‌فرض همان کاربر را تعیین می‌کند. برای چاپ راه‌دور، نام/URI، TLS، احراز هویت، firewall و دسترسی کاربر را بررسی کنید.

### تمرین مستقل

فرق cancel و lpadmin -x چیست؟

<summary>پاسخ تشریحی؛ ابتدا خودتان حل کنید</summary>
