**پیش‌نیاز:** فصل صفر و 101؛ مثال‌های بسته روی توزیع مشخص‌شده

## 102.1 — طراحی فضای دیسک

### مفهوم و کاربرد

پارتیشن یک محدوده از دیسک است؛ فایل‌سیستم روش نام‌گذاری و ذخیرهٔ فایل‌ها داخل آن و mount point پوشه‌ای است که آن محتوا از آن دیده می‌شود. `/` باید وجود داشته باشد. `/home` دادهٔ کاربران، `/var` دادهٔ متغیر مثل log و `/boot` فایل‌های بوت را دارد. ESP پارتیشن معمولاً FAT برای فایل EFI است و با `/boot` یکی نیست.

LVM انعطاف تخصیص فضا می‌دهد: PV فضای فیزیکی آماده‌شده، VG مخزن چند PV و LV سهمی از VG شبیه یک دیسک مجازی است. سپس روی LV فایل‌سیستم می‌سازیم. LVM به‌خودی‌خود backup یا تحمل خرابی نمی‌دهد.

### مثال 1: خواندن طرح فعلی

بدون نوشتن روی دیسک.

```bash
lsblk -f
findmnt /
swapon --show
```

**توضیح خط‌به‌خط:**

1. نام، نوع فایل‌سیستم، label، UUID و محل اتصال را می‌خواند.
2. دستگاهی را که ریشه از آن می‌آید نشان می‌دهد.
3. swapهای فعال را نشان می‌دهد؛ خروجی خالی یعنی swap فعال نیست.

**نتیجه و بررسی:** اگر ریشه از `/dev/mapper/...` آمده باشد ممکن است LVM یا لایهٔ رمزگذاری باشد؛ تنها از اسم نتیجه نگیرید.

### مثال 2: خواندن LVM

در VM با بستهٔ lvm2؛ این‌ها چیزی نمی‌سازند.

```bash
sudo pvs
sudo vgs
sudo lvs
```

**توضیح خط‌به‌خط:**

1. PVها، VG وابسته و فضای آزادشان را نشان می‌دهد.
2. اندازه و آزادبودن مخزنهای VG را می‌خواند.
3. LVهای ساخته‌شده، اندازه و ویژگی‌ها را می‌خواند.

**نتیجه و بررسی:** نبود PV/VG/LV در نصب بدون LVM طبیعی است. آزادبودن VG با فضای خالی داخل فایل‌سیستم LV یکی نیست.

### مثال 3: طرح روی کاغذ برای VM آموزشی

نمونهٔ طراحی، نه دستور پارتیشن‌بندی؛ اعداد الزام عمومی نیستند.

```text
ESP: 512 MiB
/: 20 GiB
/home: remaining space
swap: optional, workload-dependent
```

**توضیح خط‌به‌خط:**

1. برای بوت UEFI و فایل‌های EFI، در این طرح آموزشی اختصاص می‌دهیم.
2. برای سیستم و نرم‌افزارها فضا می‌گذاریم.
3. فضای باقی‌ماندهٔ دیسک 32 GiB را به تمرین کاربر می‌دهیم؛ جدا‌کردن home اختیاری است.
4. اندازه و وجود swap را بر اساس RAM، برنامه و نیاز hibernation تصمیم می‌گیریم؛ قانون ثابت دوبرابر RAM نداریم.

**نتیجه و بررسی:** برای سرور log، رشد `/var` مهم‌تر است؛ برای دسکتاپ دادهٔ home. جداکردن پارتیشن مانع خرابی مشترک دیسک نمی‌شود.

### اشتباه رایج و عیب‌یابی

قبل از تقسیم ریز، رشد آینده را در نظر بگیرید. خالی‌بودن home کمک نمی‌کند اگر var جدا و پر باشد.

### نکته‌های تکمیلی این سرفصل

MBR معمولاً چهار ورودی اصلی دارد؛ یکی می‌تواند extended و شامل logicalها باشد. حد حدود 2 TiB مربوط به sector منطقی 512 بایتی است. GPT محدودیت چهار primary را ندارد و نسخهٔ پشتیبان جدول دارد. BIOS با GPT هم قابل بوت است، ولی GRUB معمولاً BIOS boot partition می‌خواهد. فایل‌سیستم ریشه ممکن است رمزگذاری شود؛ دسترس‌پذیری فایل‌های بوت برای bootloader باید جدا بررسی شود.

### تمرین مستقل

سرور ثبت رویداد داری. چرا جداکردن var مفید است و چه محدودیتی ایجاد می‌کند؟

## 102.2 — GRUB و انتخاب سیستم‌عامل

### مفهوم و کاربرد

GRUB منویی برای انتخاب kernel یا سیستم‌عامل و ابزار بارگذاری آن است. GRUB 2 تنظیم تولیدشدهٔ `grub.cfg` دارد؛ منبع معمول تنظیم `/etc/default/grub` و `/etc/grub.d/` است. Legacy از `menu.lst` یا `grub.conf` استفاده می‌کرد. تغییر مستقیم فایل تولیدشده با به‌روزرسانی بعدی از بین می‌رود.

برای خودآموزی ابتدا فایل را می‌خوانیم، سپس خروجی آزمایشی می‌سازیم؛ نصب واقعی bootloader مرحله‌ای جدا با شناخت BIOS/UEFI و دیسک است.

### مثال 1: خواندن تنظیم

در Debian/Ubuntu دارای GRUB؛ اگر مسیر نیست نام فایل توزیع را بررسی کنید.

```bash
grep "^GRUB_" /etc/default/grub
ls /etc/grub.d
ls /boot
```

**توضیح خط‌به‌خط:**

1. `grep` فقط سطرهایی را می‌گیرد که با GRUB_ شروع می‌شوند؛ `^` ابتدای سطر است.
2. اسکریپت‌های سازندهٔ منو را فهرست می‌کند.
3. نسخه‌های kernel و initramfs نصب‌شده را می‌بینید.

**نتیجه و بررسی:** `GRUB_TIMEOUT=5` یعنی مهلت منو ۵ ثانیه، نه زمان لازم برای بوت کل سیستم. سیاست نمایش منو هم اثر دارد.

### مثال 2: ساخت خروجی آزمایشی

در VM Debian دارای grub-mkconfig؛ مسیر موقت خصوصی از بازنویسی فایل عمومی جلوگیری می‌کند.

```bash
grub_lab=$(mktemp -d)
sudo grub-mkconfig -o "$grub_lab/grub.cfg"
sudo grep "menuentry " "$grub_lab/grub.cfg"
```

**توضیح خط‌به‌خط:**

1. یک پوشهٔ موقت یکتا ساخته و مسیرش را ذخیره می‌کند.
2. `-o` مسیر خروجی است؛ به فایل فعال `/boot/grub/grub.cfg` دست نمی‌زنیم.
3. ورودی‌های تولیدشده را می‌خواند؛ وجود ورودی تضمین بوت موفق نیست.

**نتیجه و بررسی:** در بعضی RPMها نام ابزار `grub2-mkconfig` است. پس از بررسی، فقط همین فایل و پوشهٔ موقت را حذف کنید؛ به /boot کاری نداشته باشید.

### مثال 3: معنای منوی Legacy

صرفاً نمونهٔ تاریخی برای خواندن؛ نام فایل‌های kernel باید در سیستم واقعی موجود باشند.

```text
title Lab Linux
root (hd0,0)
kernel /vmlinuz root=/dev/vda2 ro
initrd /initrd.img
```

**توضیح خط‌به‌خط:**

1. عنوانی که در منوی GRUB Legacy دیده می‌شود.
2. دیسک اول و پارتیشن اول در شماره‌گذاری Legacy را انتخاب می‌کند؛ با GRUB 2 یکسان فرض نکنید.
3. kernel از پارتیشن انتخابی بارگذاری می‌شود؛ root= ریشهٔ لینوکس و ro اتصال اولیهٔ خواندنی را مشخص می‌کند.
4. فایل محیط اولیهٔ متناسب با همان kernel را معرفی می‌کند.

**نتیجه و بررسی:** این نمونه به فایل واقعی نیاز دارد و نباید در GRUB 2 کپی شود. در shell قدیمی `root (hd0,0)` و سپس `setup (hd0)` نصب تاریخی روی دیسک اول بود؛ آن را روی VM امروزی اجرا نکنید.

### اشتباه رایج و عیب‌یابی

وقتی نسخهٔ جدید kernel خراب است، ابتدا ورودی قبلیِ شناخته‌شده را امتحان کنید. حذف همهٔ kernelهای قدیمی راه بازیابی را از بین می‌برد.

### نکته‌های تکمیلی این سرفصل

در کنسول GRUB 2، `ls` دستگاه‌ها، `ls (hd0,gpt1)/` محتوای یک پارتیشن و `set` متغیرها را می‌خواند. `insmod` ماژول GRUB را بارگذاری می‌کند؛ با insmod لینوکس فرق دارد. `linux` مسیر kernel و پارامترها، `initrd` مسیر initramfs و `boot` شروع اجراست. ابتدا با ls مسیر واقعی را کشف کنید.

نصب روی VM کاملاً مصرفی BIOS پس از شناسایی دیسک ممکن است شکل `grub-install --target=i386-pc /dev/vda` داشته باشد: target یعنی نوع bootloader و `/dev/vda` کل دیسک آزمایش است. برای UEFI x86_64، شکل `grub-install --target=x86_64-efi --efi-directory=/boot/efi --bootloader-id=LabLinux` است: ESP باید واقعاً در /boot/efi متصل باشد. در سیستم Secure Boot، دستور توزیع و بسته‌های signed/shim مقدم‌اند؛ این دو شکل را جایگزین بی‌فکرانهٔ روش توزیع نکنید. قبل از نصب، snapshot و ISO بازیابی داشته باشید؛ پس از نصب، خروجی تولیدشده و بوت کنسولی را بررسی کنید. مسیر دوم بوت را نیز عملاً آزمایش کنید؛ کپی پوشهٔ boot به‌تنهایی کافی نیست.

## 102.3 — کتابخانه‌های مشترک

### مفهوم و کاربرد

کتابخانه مجموعه‌ای از کد آماده است. چند برنامه می‌توانند از کتابخانهٔ مشترکی مثل libc استفاده کنند. dynamic linker هنگام اجرا آن را پیدا می‌کند. پس موجودبودن فایل اجرایی همیشه برای اجرای برنامه کافی نیست. پسوند `.so` نشانهٔ رایج کتابخانهٔ اشتراکی است.

### مثال 1: وابستگی برنامهٔ شناخته‌شده

فقط روی برنامهٔ معتبر نصب‌شدهٔ سیستم.

```bash
file /bin/ls
ldd /bin/ls
```

**توضیح خط‌به‌خط:**

1. نوع فایل اجرایی و اطلاعات معماری را می‌خواند.
2. وابستگی‌ها و مسیر حل‌شدهٔ آن‌ها را نمایش می‌دهد.

**نتیجه و بررسی:** سطر `libc.so.6 => /lib/...` مسیر حل‌شده است؛ `not found` یعنی یکی از وابستگی‌ها پیدا نشده. روی فایل ناشناس ldd اجرا نکنید.

### مثال 2: فهرست cache

فقط خواندن.

```bash
ldconfig -p
cat /etc/ld.so.conf
ls /etc/ld.so.conf.d
```

**توضیح خط‌به‌خط:**

1. `-p` cache کتابخانه‌های قابل شناسایی را چاپ می‌کند؛ با ldconfig بدون گزینه فرق دارد.
2. تنظیم مسیرهای کتابخانه را می‌خواند؛ ممکن است با include فایل‌های دیگری را معرفی کند.
3. فایل‌های تنظیم اضافی را، اگر این پوشه وجود دارد، فهرست می‌کند.

**نتیجه و بررسی:** cache فهرست همهٔ فایل‌های دیسک نیست. روی بعضی سیستم‌ها برای یافتن ابزار باید مسیر `/sbin/ldconfig` را صریح بدهید.

### مثال 3: اثر موقت یک متغیر

دایرکتوری آموزشی خالی و برنامهٔ معتبر؛ دستکاری کتابخانهٔ سیستم نداریم.

```bash
lib_lab=$(mktemp -d)
LD_LIBRARY_PATH="$lib_lab" /bin/ls -d "$lib_lab"
rmdir "$lib_lab"
```

**توضیح خط‌به‌خط:**

1. پوشه‌ای خالی و یکتا می‌سازد.
2. متغیر فقط برای این اجرا تنظیم می‌شود؛ linker مسیرهای عادی را نیز طبق قواعدش بررسی می‌کند. `-d` خود پوشه را نشان می‌دهد.
3. پوشهٔ خالی را حذف می‌کند؛ تنظیم محیط parent تغییری نکرده است.

**نتیجه و بررسی:** دستور ls همچنان اجرا می‌شود، چون کتابخانه‌های مورد نیاز در مسیرهای استاندارد هستند.

### اشتباه رایج و عیب‌یابی

کتابخانهٔ تصادفی از اینترنت کپی نکنید. نام بسته، معماری 32/64 بیت و نسخهٔ ABI را بررسی کنید. LD_LIBRARY_PATH سراسری می‌تواند کتابخانهٔ اشتباه بار کند.

### نکته‌های تکمیلی این سرفصل

مسیرهای رایج `/lib` و `/usr/lib` و زیردایرکتوری معماری هستند. در ELF، RPATH/RUNPATH، محیط، cache و مسیرهای پیش‌فرض در جست‌وجو نقش دارند و ترتیب دقیق به نوع ELF و حالت اجرای امن وابسته است. برای خطای missing ابتدا بستهٔ مالک کتابخانه را با ابزار بسته پیدا و از مخزن معتبر تعمیر کنید.

## 102.4 — بسته‌های Debian و Ubuntu

### مفهوم و کاربرد

بسته فایل‌های برنامه و اطلاعات نصب را یکجا نگه می‌دارد. Repository مخزن بسته‌هاست. Dependency یعنی برنامه به بستهٔ دیگری نیاز دارد. `dpkg` بستهٔ deb و پایگاه نصب محلی را مدیریت می‌کند؛ APT مخزن را جست‌وجو و وابستگی را حل می‌کند. update فهرست را تازه می‌کند و upgrade نسخهٔ نصب‌شده را عوض می‌کند.

### مثال 1: نصب یک ابزار کوچک

در VM Debian/Ubuntu با اینترنت؛ فهرست تغییر را قبل از قبول بخوانید.

```bash
sudo apt update
apt show tree
sudo apt install tree
tree --version
```

**توضیح خط‌به‌خط:**

1. فهرست بسته‌های مخزن را تازه می‌کند؛ خود برنامه‌ها ارتقا نمی‌یابند.
2. توضیح و نسخه و وابستگی tree را می‌خواند.
3. tree و وابستگی لازم را پس از تأیید نصب می‌کند؛ -y عمداً استفاده نشده است.
4. نسخهٔ قابل اجرا را نشان می‌دهد.

**نتیجه و بررسی:** اگر Unable to locate package دیدید، موفقیت update و مخزن‌های فعال را بررسی کنید؛ نام بسته و نام executable همیشه یکی نیست.

### مثال 2: مالک فایل و وضعیت

بعد از نصب مثال قبل.

```bash
dpkg -L tree
dpkg -S /usr/bin/tree
dpkg-query -W tree
dpkg --verify tree
```

**توضیح خط‌به‌خط:**

1. `-L` بزرگ فهرست فایل‌های بستهٔ نصب‌شده را می‌دهد.
2. `-S` بزرگ نام بستهٔ مالک این مسیر را جست‌وجو می‌کند.
3. `-W` وضعیت نسخهٔ بسته را به‌شکل مختصر می‌خواند.
4. ویژگی‌های ثبت‌شدهٔ قابل بررسی بسته را مقایسه می‌کند؛ سکوت معمولاً یعنی اختلافی در موارد بررسی‌شده نیست.

**نتیجه و بررسی:** خروجی مالک معمولاً `tree: /usr/bin/tree` است. verify به‌تنهایی اثبات پاک‌بودن سیستم نیست؛ همهٔ فایل‌ها و همهٔ ویژگی‌ها را پوشش نمی‌دهد.

### مثال 3: برنامهٔ ارتقا و پاک‌سازی

در همان VM؛ tree نباید وابستگی مهمِ کار دیگری باشد.

```bash
apt-cache policy tree
apt-get --simulate upgrade
sudo apt remove tree
sudo apt purge tree
```

**توضیح خط‌به‌خط:**

1. نسخهٔ نصب‌شده، candidate و منشأ نسخه‌ها را نشان می‌دهد.
2. اقدامات upgrade را محاسبه می‌کند و اعمال نمی‌کند.
3. بسته را حذف می‌کند؛ conffileها ممکن است باقی بمانند.
4. تنظیم‌های مدیریت‌شدهٔ همان بسته را نیز پاک می‌کند؛ دادهٔ home الزاماً حذف نمی‌شود.

**نتیجه و بررسی:** با `command -v tree` بررسی کنید دیگر executable در PATH نباشد. شبیه‌سازی بدون root ممکن است به بعضی تنظیم‌ها دسترسی نداشته باشد.

### اشتباه رایج و عیب‌یابی

`dpkg -i ./file.deb` وابستگی گمشده را خودش دانلود نمی‌کند. برای فایل معتبر محلی `apt install ./file.deb` می‌تواند وابستگی را حل کند. قفل بسته را با حذف lock دور نزنید؛ مدیر بستهٔ دیگر را بررسی کنید.

### نکته‌های تکمیلی این سرفصل

`apt-cache depends tree` وابستگی، `apt-cache search tree` جست‌وجوی نام/توضیح، `dpkg -I ./file.deb` اطلاعات فایل بسته و `dpkg -c ./file.deb` محتویات آن است؛ file.deb باید فایل واقعی معتبر باشد. `sudo dpkg-reconfigure tzdata` پرسش‌های تنظیم بسته را دوباره اجرا می‌کند و timezone را ممکن است تغییر دهد.

`apt upgrade` می‌تواند وابستگی جدید نصب کند ولی بستهٔ نصب‌شده را برای ارتقا حذف نمی‌کند؛ `apt-get upgrade` به‌طور پیش‌فرض محافظه‌کارتر است. `apt full-upgrade` و `apt-get dist-upgrade` ممکن است حذف هم پیشنهاد کنند. `--reinstall install tree` با apt-get نصب مجدد است. فایل‌های مخزن در `/etc/apt/sources.list` و `/etc/apt/sources.list.d/` هستند؛ قالب جدید deb822 با پسوند sources هم رایج است. `apt-get` برای اسکریپت مناسب‌تر از رابط انسانی apt است.

### تمرین مستقل

برای یافتن فایل در بسته‌ای که هنوز نصب نیست آیا dpkg -S کافی است؟

<details>
<summary>پاسخ تشریحی؛ ابتدا خودتان حل کنید</summary>

خیر؛ dpkg -S پایگاه نصب محلی را می‌گردد. بستهٔ apt-file را نصب، با `sudo apt-file update` فهرستش را تازه و با `apt-file search /usr/bin/tree` محتویات مخزن را جست‌وجو می‌کنیم.

</details>

## 102.5 — بسته‌های RPM، YUM و Zypper

### مفهوم و کاربرد

RPM هم فرمت بسته است و هم ابزار محلی. DNF و YUM روی مخزن و حل وابستگی کار می‌کنند؛ Zypper همین نقش را در SUSE دارد. همهٔ این ابزارها را روی یک توزیع باهم جایگزین یکدیگر نکنید. مثال نخست برای Rocky/Alma/Fedora، مثال سوم برای openSUSE است.

### مثال 1: نصب و پرس‌وجو با DNF

VM خانوادهٔ RPM؛ اینترنت و مخزن معتبر لازم است.

```bash
dnf info tree
sudo dnf install tree
rpm -qi tree
rpm -ql tree
rpm -qf /usr/bin/tree
```

**توضیح خط‌به‌خط:**

1. اطلاعات بسته را می‌خواند.
2. نصب و وابستگی‌ها را پیشنهاد و پس از تأیید اجرا می‌کند.
3. `-q` پرس‌وجو و `-i` اطلاعات بستهٔ نصب‌شده است.
4. `-l` همراه q فایل‌های بسته را لیست می‌کند.
5. `-f` همراه q مالک فایل را پیدا می‌کند.

**نتیجه و بررسی:** فرق `rpm -i FILE.rpm` با `rpm -qi NAME` مهم است؛ اولی نصب و دومی پرس‌وجو است.

### مثال 2: بررسی و مدیریت نسخه

بعد از مثال اول؛ تغییرات تنها روی tree آزمایش.

```bash
rpm -V tree
dnf provides /usr/bin/tree
sudo dnf reinstall tree
sudo dnf upgrade tree
sudo dnf remove tree
```

**توضیح خط‌به‌خط:**

1. ویژگی‌های فایل‌های نصب‌شده را با پایگاه RPM مقایسه می‌کند؛ V بزرگ است.
2. بسته‌های مخزنِ فراهم‌کنندهٔ مسیر را جست‌وجو می‌کند.
3. فایل‌های بسته را دوباره نصب می‌کند؛ ابزار تعمیر فایل بسته است، نه backup داده.
4. ارتقای همین بسته را پیشنهاد می‌کند.
5. حذف و اثر آن روی وابستگی‌ها را پیش از تأیید نشان می‌دهد.

**نتیجه و بررسی:** در rpm -V علامت `5` اختلاف digest، `S` اندازه، `M` mode و `T` زمان است. تغییر فایل تنظیم لزوماً نفوذ نیست؛ باید علت را بدانید.

### مثال 3: همان کار در SUSE

این مثال فقط روی VM دارای Zypper اجرا شود.

```bash
zypper search tree
sudo zypper refresh
sudo zypper install tree
sudo zypper update tree
sudo zypper remove tree
```

**توضیح خط‌به‌خط:**

1. بسته را با نام جست‌وجو می‌کند.
2. metadata مخزن‌ها را تازه می‌کند.
3. بسته را با حل وابستگی نصب می‌کند.
4. نسخهٔ جدید همین بسته را پیشنهاد می‌کند.
5. tree را حذف می‌کند؛ فهرست transaction را بخوانید.

**نتیجه و بررسی:** ابزار محلی rpm روی SUSE هم قابل استفاده است؛ اما تنظیم مخزن آن را با yum.conf اشتباه نگیرید.

### اشتباه رایج و عیب‌یابی

برای ردکردن خطای وابستگی از --nodeps استفاده نکنید. امضای ناشناس با امضای معتبر از کلید مورد اعتماد برابر نیست.

### نکته‌های تکمیلی این سرفصل

`rpm -Uvh ./package.rpm` یعنی نصب/ارتقا (`U`)، نمایش جزئیات (`v`) و نوار پیشرفت (`h`)؛ `rpm -e NAME` حذف محلی است. `rpm -qpR ./package.rpm` وابستگی فایل بسته را بدون نصب می‌خواند: q پرس‌وجو، p فایل بسته، R نیازمندی‌ها. `yum install/info/update/remove NAME` همتای تاریخی عملیات است؛ `/etc/yum.conf` تنظیم عمومی و `/etc/yum.repos.d/*.repo` مخزن‌ها هستند. `dnf repolist` و `zypper repos` مخزن‌های فعال را نشان می‌دهند.

برای استخراج فایل معتبر بدون نصب، در پوشهٔ خالی `rpm2cpio /path/package.rpm | cpio -idmv --no-absolute-filenames` استفاده می‌شود: rpm2cpio payload را تبدیل، pipe آن را منتقل و cpio با i استخراج، d ساخت پوشه، m حفظ زمان و v نمایش نام می‌کند. ابتدا با `rpm -qpl /path/package.rpm` نام مسیرها را بخوانید؛ فقط بستهٔ مورد اعتماد را در VM باز کنید.

### تمرین مستقل

فرق rpm -V NAME و rpm -K FILE.rpm را توضیح دهید.

<details>
<summary>پاسخ تشریحی؛ ابتدا خودتان حل کنید</summary>

اولی فایل نصب‌شده را با metadata پایگاه مقایسه می‌کند؛ دومی digest و امضای فایل بسته را بررسی می‌کند. برای معتبر‌دانستن امضا باید کلید امضاکننده را از منبع معتبر بشناسیم.

</details>

## 102.6 — لینوکس داخل ماشین مجازی و ابر

### مفهوم و کاربرد

VM یک رایانهٔ مجازی با kernel مستقل است. Container معمولاً kernel میزبان را شریک می‌شود. container سیستمی محیط شبیه یک OS و container برنامه‌ای محیط لازم یک برنامه را می‌دهد. Image الگوی ساخت است و Instance نمونهٔ ساخته‌شده از آن. در IaaS، CPU/RAM، دیسک بلوکی و شبکهٔ مجازی جدا تخصیص داده می‌شوند.

Clone بیت‌های دیسک را تکثیر می‌کند ولی هویت ماشین نباید تکثیر شود. machine-id، کلید host مربوط به SSH، hostname و تنظیم MAC/DHCP باید با روش رسمی ساخت template بازتولید شوند.

### مثال 1: محیط مجازی

این دستورها فقط سرنخ هستند.

```bash
systemd-detect-virt
uname -r
lsblk
```

**توضیح خط‌به‌خط:**

1. نوع مجازی‌سازی تشخیص‌داده‌شده را چاپ می‌کند؛ none و کد غیرصفر ممکن است یعنی چیزی تشخیص داده نشده.
2. نسخهٔ kernel در حال اجرا را نشان می‌دهد.
3. دیسک‌های قابل مشاهده را نشان می‌دهد؛ container لزوماً نمای کامل یا قابل مدیریت دیسک ندارد.

**نتیجه و بررسی:** یکسانی uname در دو container به‌معنی دو VM مستقل نیست؛ اغلب kernel میزبان مشترک است.

### مثال 2: بررسی هویت دو clone

روی هر VM جداگانه؛ خروجی شناسه‌ها را عمومی منتشر نکنید.

```bash
hostnamectl --static
sha256sum /etc/machine-id
ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
```

**توضیح خط‌به‌خط:**

1. نام ثابت ماشین را می‌خواند.
2. برای مقایسهٔ محلی، digest شناسه را می‌دهد؛ خود شناسه را تغییر نمی‌دهد.
3. `-l` نمایش fingerprint و `-f` انتخاب فایل کلید عمومی host است.

**نتیجه و بررسی:** fingerprint کلید host و machine-id دو نمونه باید مستقل باشند. اگر SSH نصب نیست فایل وجود ندارد؛ فایل خصوصی را چاپ نکنید.

### مثال 3: شناخت cloud-init

فقط روی image دارای cloud-init؛ آن را روی نصب معمولی لازم نداریم.

```bash
cloud-init status --long
systemctl status cloud-init.service --no-pager
ls /var/lib/cloud/instances
```

**توضیح خط‌به‌خط:**

1. وضعیت اجرای تنظیم اولیه و جزئیات خطا را می‌خواند.
2. وضعیت یکی از مراحل cloud-init را نشان می‌دهد؛ inactive پس از پایان یک مرحله الزاماً خطا نیست.
3. دایرکتوری state نمونه‌ها را فهرست می‌کند؛ user-data ممکن است محرمانه باشد و نباید چاپ شود.

**نتیجه و بررسی:** cloud-init نام، کاربر، کلید و شبکهٔ اولیه را از دادهٔ provisioning تنظیم می‌کند؛ نصب‌بودنش اثبات اجرای درست همهٔ مراحل نیست.

### اشتباه رایج و عیب‌یابی

پاک‌کردن machine-id یا کلید SSH از ماشین در حال استفاده روش معمول تعمیر نیست. template را در حالت آماده‌سازی و مطابق مستندات توزیع اصلاح کنید.

### نکته‌های تکمیلی این سرفصل

VirtIO، VMware tools، QEMU guest agent و Hyper-V integration به ارتباط مهمان و hypervisor کمک می‌کنند؛ shutdown مرتب، کارایی شبکه/دیسک و گزارش IP از کاربردهاست. guest agent با kernel driver یک چیز نیست. پس از ساخت دو clone، هم یکتایی هویت و هم شبکه و سرویس‌ها را بررسی کنید.

### تمرین مستقل

چرا snapshot همان backup خارج از میزبان نیست؟
