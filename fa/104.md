# 104 — فایل‌سیستم، اتصال دیسک، مجوز و مسیرها

[فهرست دوره](README.md)

**پیش‌نیاز:** فصل‌های صفر، 102 و 103؛ تمرین دیسک فقط داخل VM مصرفی

مثال‌ها را به ترتیب هر درس در همان ترمینال اجرا کنید. «خروجی نمونه» عین خروجی همهٔ دستگاه‌ها نیست؛ نام‌ها، شماره‌ها و نسخه‌ها ممکن است فرق کنند. بلوک `text` داده یا پاسخ تعاملی است و نباید به‌عنوان دستور Bash اجرا شود.

## 104.1 — پارتیشن و فایل‌سیستم را جدا یاد بگیریم

### مفهوم و کاربرد

جدول پارتیشن تعیین می‌کند هر بخش دیسک کجاست؛ mkfs داخل یک بخش ساختار فایل می‌سازد. هر دو عمل نوشتن‌اند. برای شروع بدون انتخاب دستگاه واقعی، یک فایل image معمولی می‌سازیم و فقط همان فایل را پارتیشن‌بندی می‌کنیم. مثال ext4 بعدی فایل جداست و جدول مثال اول را فرمت نمی‌کند.

ext2 بدون journal، ext3 با journal و ext4 توسعه‌یافتهٔ آن خانواده است. XFS فایل‌سیستم journalدار مقیاس‌پذیر است. VFAT/exFAT برای تبادل فایل رایج‌اند ولی مجوز Unix مثل ext4 ندارند. Btrfs قابلیت checksum، subvolume، compression و چنددستگاهی دارد؛ subvolume یک پارتیشن نیست.

### مثال 1: پارتیشن داخل فایل

ابزار util-linux و حداقل 128 MiB فضای قابل تخصیص؛ دستورها فقط فایل یکتای جدید را تغییر می‌دهند.

```bash
disk_lab=$(mktemp -d)
cd "$disk_lab"
truncate -s 128M partition.img
fdisk partition.img
```

**توضیح خط‌به‌خط:**

1. پوشهٔ یکتا می‌سازیم تا فایل قدیمی بازنویسی نشود.
2. وارد پوشه می‌شویم.
3. فایل sparse با اندازهٔ منطقی 128 MiB می‌سازد؛ هنوز فایل‌سیستم ندارد.
4. ویرایشگر روی فایل عادی باز می‌شود، نه /dev/دیسک. پاسخ‌های زیر را جدا وارد کنید.

**نتیجه و بررسی:** در fdisk: `g` ساخت GPT خالی؛ `n` پارتیشن جدید؛ Enter برای شماره و Enter برای sector آغاز؛ `+64M` اندازه؛ `p` بازبینی؛ `w` ثبت و خروج. اگر اشتباه کردید پیش از w با q خارج شوید. سپس `fdisk -l partition.img` جدول را بخوانید. هیچ block device تازه به سیستم افزوده نمی‌شود.

### مثال 2: ساخت فایل‌سیستم روی image دیگر

e2fsprogs لازم است؛ این فایل جدول پارتیشن ندارد و عمداً کل آن یک filesystem است.

```bash
truncate -s 64M filesystem.img
mkfs.ext4 -L LPICLAB filesystem.img
blkid -p filesystem.img
```

**توضیح خط‌به‌خط:**

1. فایل جدا با ظرفیت منطقی 64 MiB می‌سازد.
2. ext4 می‌سازد؛ L برچسب LPICLAB است؛ تمام محتوای همین image جایگزین می‌شود.
3. `-p` مستقیماً امضای فایل را بررسی می‌کند؛ UUID، label و ext4 را انتظار داریم.

**نتیجه و بررسی:** partition.img و filesystem.img دو تمرین مستقل‌اند. ساخت جدول به‌تنهایی فایل‌سیستم نمی‌سازد.

### مثال 3: آماده‌سازی swap بدون فعال‌کردن

در همان پوشه، فقط نمایش ساختار swap؛ هیچ حافظهٔ سیستم تغییر نمی‌کند.

```bash
dd if=/dev/zero of=swap.img bs=1M count=16 status=none
chmod 600 swap.img
mkswap swap.img
blkid -p swap.img
```

**توضیح خط‌به‌خط:**

1. شانزده بلوک یک MiB صفر در فایل تازه می‌نویسد؛ فایل sparse نمی‌سازیم.
2. تنها مالک حق خواندن/نوشتن دارد.
3. امضای swap روی همین فایل می‌نویسد؛ آن را فعال نمی‌کند.
4. نوع swap و UUID را تأیید می‌کند.

**نتیجه و بررسی:** `swapon --show` تغییری نکرده چون swapon اجرا نکردیم. swap کمک به فشار حافظه است و تضمین جلوگیری از OOM یا کندی نیست.

### اشتباه رایج و عیب‌یابی

هیچ‌یک از مسیرهای فایل را با /dev/sda جایگزین نکنید. فایل image حاوی جدول را با mkfs کل‌فایل فرمت نکنید، وگرنه جدولش پاک می‌شود.

### نکته‌های تکمیلی این سرفصل

برای تکرار در فایل‌های مستقل می‌توانید با truncate image خالی بسازید و `gdisk FILE` (GPT؛ n ساخت، p بازبینی، w ثبت) یا `parted FILE` را امتحان کنید. در parted، `mklabel gpt` جدول جدید، `mkpart primary 1MiB 65MiB` محدوده، `print` نمایش و `quit` خروج است؛ برخلاف fdisk، بسیاری تغییرهای parted فوری اعمال می‌شوند.

روی پارتیشن مصرفیِ تأییدشده، سازنده‌ها `mkfs.ext2`، `mkfs.ext3`، `mkfs.ext4`، `mkfs.xfs`، `mkfs.vfat` و `mkfs.exfat` هستند. `mke2fs -t ext4 FILE` هم سازندهٔ ext4 است؛ اسم fsck ندارد و تعمیر نیست. هرکدام بسته و حداقل اندازهٔ خود را دارند؛ فایل 64 MiB برای همه مناسب نیست. `btrfs subvolume list MOUNTPOINT` زیردرخت‌ها و `btrfs filesystem show` دستگاه‌های آن را نشان می‌دهد؛ فقط روی Btrfs کاربرد دارند.

در VM با پارتیشن swap اختصاصی، پس از mkswap، `sudo swapon DEVICE` فعال و `sudo swapoff DEVICE` غیرفعال می‌کند؛ ابتدا DEVICE واقعی را دوبار شناسایی کنید. swapoff به RAM کافی نیاز دارد. نمونهٔ fstab: `UUID=ACTUAL_UUID none swap sw 0 0`؛ ACTUAL_UUID را از blkid بگیرید. فعال‌سازی fstab با swapon --all است، نه mount -a. محدودیت swapfile در فایل‌سیستم‌هایی مثل Btrfs را با مستندات همان فایل‌سیستم بررسی کنید.

### تمرین مستقل

چرا پس از fdisk هنوز mkdir روی پارتیشن نمی‌توان زد؟

## 104.2 — فضای خالی، inode و سلامت

### مفهوم و کاربرد

فایل‌سیستم هم بلوک داده دارد و هم metadata مربوط به فایل‌ها. inode اطلاعاتی مثل مالک، مجوز و نشانی داده را نگه می‌دارد؛ نام در ورودی پوشه است. ممکن است فضای بایتی آزاد باشد اما inode تمام شود. df وضعیت کل فایل‌سیستم و du مصرف فایل‌های قابل پیمایش را می‌خواند.

تعمیر فایل‌سیستم عملی متفاوت از فرمت است. بررسی اصلاح‌کننده را روی فایل‌سیستم mounted اجرا نکنید. ابتدا backup، توقف استفاده و جداسازی؛ ریشه معمولاً محیط recovery می‌خواهد.

### مثال 1: کدام فضا پر است؟

فقط خواندن؛ پوشهٔ home خودتان.

```bash
df -hT "$HOME"
df -i "$HOME"
du -sh "$HOME"
```

**توضیح خط‌به‌خط:**

1. h واحد خوانا، T نوع و مسیر HOME فایل‌سیستم مربوط را انتخاب می‌کند.
2. inodeهای کل، مصرف‌شده و آزاد را نشان می‌دهد.
3. s جمع مصرف و h واحد خواناست؛ ممکن است پیمایش home بزرگ طول بکشد.

**نتیجه و بررسی:** اگر IUse% نزدیک 100 و Use% پایین است، تعداد زیاد فایل ریز را بررسی کنید. du فقط فایل‌های قابل دسترس را حساب می‌کند؛ برابر‌بودن دقیق با df الزامی نیست.

### مثال 2: چک بدون تعمیر روی image

فایل filesystem.img از 104.1 را در همان shell و پوشه داریم؛ هنوز mount نشده است.

```bash
e2fsck -fn filesystem.img
tune2fs -l filesystem.img
```

**توضیح خط‌به‌خط:**

1. f بررسی اجباری، n پاسخ منفی و بازکردن فقط‌خواندنی؛ چیزی تعمیر نمی‌شود.
2. l ویژگی‌های superblock مثل block count، inode count و label را می‌خواند.

**نتیجه و بررسی:** برای image تازه انتظار خطای خرابی نداریم. بدون -n، e2fsck ممکن است تغییر پیشنهاد/اعمال کند. tune2fs گزینه‌های تغییردهنده هم دارد؛ اینجا فقط l است.

### مثال 3: اثر اندازهٔ منطقی و واقعی

در یک پوشهٔ تمرین با نام تازه؛ مثال مستقل است.

```bash
space_lab=$(mktemp -d)
truncate -s 32M "$space_lab/sparse.img"
ls -lh "$space_lab/sparse.img"
du -h "$space_lab/sparse.img"
```

**توضیح خط‌به‌خط:**

1. پوشهٔ یکتا می‌سازد.
2. اندازهٔ منطقی را 32 MiB می‌کند بدون الزام نوشتن همهٔ بلوک‌ها.
3. اندازهٔ منطقی فایل را می‌خواند.
4. بلوک‌های تخصیص‌یافته را می‌سنجد؛ روی سیستم پشتیبان sparse می‌تواند بسیار کمتر باشد.

**نتیجه و بررسی:** اختلاف این دو خروجی طبیعی است؛ فضای ظاهری فایل با فضای واقعاً تخصیص‌یافته یک مفهوم نیست.

### اشتباه رایج و عیب‌یابی

خطای unmount را با `|| true` مخفی و سپس fsck اجرا نکنید. اگر busy است ابتدا پردازهٔ استفاده‌کننده را پیدا کنید. فایل حذف‌شدهٔ هنوز باز می‌تواند علت df زیاد و du کم باشد.

### نکته‌های تکمیلی این سرفصل

`fsck` یک front end است و checker مناسب نوع فایل‌سیستم را صدا می‌زند. `xfs_db -r DEVICE` بازکردن فقط‌خواندنی پایگاه XFS است؛ در محیط تعاملی `quit` خارج می‌شود. `xfs_fsr` بازآرایی extent برای کاهش fragmentation است، نه تعمیر عمومی خرابی. `tune2fs -l` خواندنی است ولی سایر گزینه‌ها تنظیم را عوض می‌کنند. از `fsck -y` خودکار روی دادهٔ ارزشمند استفاده نکنید؛ تعمیر ممکن است بخش‌های غیرقابل‌بازیابی را حذف کند.

### تمرین مستقل

برای XFS از e2fsck استفاده می‌کنید؟ روش تشخیص غیرتغییردهنده چیست؟

<details>
<summary>پاسخ تشریحی؛ ابتدا خودتان حل کنید</summary>

خیر. روی دستگاه XFS جداشده و درست‌شناسایی‌شده `xfs_repair -n DEVICE` بررسی غیرتغییردهنده است. e2fsck مخصوص خانوادهٔ ext است.

</details>

## 104.3 — Mount و fstab

### مفهوم و کاربرد

Mount محتوای فایل‌سیستم را به یک پوشه وصل می‌کند؛ فایل‌های قبلی پوشهٔ مقصد تا زمان unmount پشت آن پنهان می‌شوند، حذف نمی‌شوند. UUID شناسهٔ فایل‌سیستم و LABEL اسم قابل انتخاب آن است؛ نام دیسک ممکن است با اتصال مجدد عوض شود.

در تمرین مقدماتی، image ext4 از 104.1 را فقط‌خواندنی mount می‌کنیم. به قابلیت loop و mount در VM نیاز داریم؛ در container ممکن است مجاز نباشد.

### مثال 1: اتصال image

در پوشه و shell تمرین 104.1؛ روی VM مصرفی.

```bash
mkdir -p image-mount
sudo mount -o loop,ro filesystem.img image-mount
findmnt --target "$PWD/image-mount"
ls image-mount
sudo umount "$PWD/image-mount"
```

**توضیح خط‌به‌خط:**

1. پوشهٔ مقصد خالی می‌سازد.
2. o گزینه‌ها، loop استفاده از فایل به‌عنوان دستگاه و ro فقط‌خواندنی است.
3. فایل‌سیستم پوشانندهٔ مسیر مطلق را نشان می‌دهد.
4. محتوا را می‌خواند؛ ext4 تازه معمولاً lost+found دارد.
5. اتصال را جدا می‌کند؛ فایل image پاک نمی‌شود.

**نتیجه و بررسی:** با `mountpoint image-mount` باید پس از جداسازی اعلام شود mount point نیست. اگر busy است، از داخل پوشه خارج شوید و برنامهٔ استفاده‌کننده را ببندید.

### مثال 2: خواندن یک سطر fstab

فقط تحلیل؛ UUID نمونه را در تنظیم واقعی کپی نکنید.

```fstab
UUID=ACTUAL_UUID /srv/lab ext4 defaults,nofail 0 2
```

**توضیح خط‌به‌خط:**

1. شش فیلد: شناسهٔ واقعی، مقصد، نوع، گزینه‌ها، dump و ترتیب بررسی.

**نتیجه و بررسی:** defaults گزینه‌های پایه، nofail عدم الزامی‌بودن این mount برای boot معمول، 0 غیرفعال‌بودن dump و 2 بررسی پس از ریشه است. nofail خطای تنظیم را اصلاح نمی‌کند.

### مثال 3: اعتبارسنجی تنظیم فعلی

فقط خواندن و بررسی؛ فایل سیستم را اینجا ویرایش نمی‌کنیم.

```bash
cat /etc/fstab
sudo findmnt --verify --verbose
systemd-escape --path --suffix=mount /srv/lab
```

**توضیح خط‌به‌خط:**

1. تنظیم اتصال هنگام boot را می‌خواند.
2. درستی قابل بررسیِ fstab، مقصد و منبع را گزارش می‌کند؛ mount انجام نمی‌دهد.
3. نام systemd متناظر مسیر را تولید می‌کند.

**نتیجه و بررسی:** نام تولیدشده `srv-lab.mount` است. این دستور آن واحد را ایجاد نمی‌کند؛ systemd می‌تواند واحد را از fstab بسازد.

### اشتباه رایج و عیب‌یابی

`umount` املای درست است. اگر busy شد با `fuser -vm MOUNTPOINT` کاربران mount و `lsof` فایل‌های باز را ببینید؛ `-k` به fuser اضافه نکنید چون پردازه می‌کشد.

### نکته‌های تکمیلی این سرفصل

چرخهٔ fstab روی دیسک آزمایش واقعی: UUID را از blkid بگیرید، مقصد را با sudo mkdir بسازید، با `sudo cp -a /etc/fstab /etc/fstab.before-lpic` backup بگیرید (اگر backup قبلی هست نام تازه انتخاب کنید)، فقط سطر lab را با sudoedit اضافه کنید، findmnt --verify بزنید و خطا را رفع کنید، در systemd `sudo systemctl daemon-reload` بزنید و با `sudo mount /srv/lab` فقط همان entry را آزمایش کنید. `mount -a` همهٔ entryهای واجد شرایط را پردازش می‌کند، بنابراین برای آزمایش یک تغییر محدود اولین انتخاب نیست. برای پایان، unmount، حذف فقط سطر lab و daemon-reload لازم است؛ قبل از جداکردن دیسک انجام دهید.

`ro/rw` خواندنی/نوشتنی، `noexec` منع اجرای مستقیم، `nosuid` منع اثر SUID/SGID، `nodev` بی‌اثرکردن device node، `users` اجازهٔ unmount برای همهٔ کاربران و `user` فقط کاربر mountکننده است. noexec مانع خواندن script توسط interpreter نیست. در fstab ریشه معمولاً pass=1 و فایل‌سیستم‌های دیگرِ قابل fsck مقدار 2 دارند؛ نوع فایل‌سیستم و ابزار بررسی را در نظر بگیرید. `/media` رایج برای رسانهٔ جداشدنی و `/mnt` برای اتصال موقت مدیر است.

### تمرین مستقل

برای یک USB که کاربر خودش وصل کند اما در بوت خودکار وصل نشود کدام گزینه‌ها مناسب‌اند؟

<details>
<summary>پاسخ تشریحی؛ ابتدا خودتان حل کنید</summary>

برای USB مشخص `noauto,user,nodev,nosuid`؛ noauto عدم اتصال خودکار، user اجازه به کاربر mountکننده برای unmount، nodev بی‌اثرکردن device node و nosuid بی‌اثرکردن بیت‌های افزایش امتیاز است. user معمولاً noexec نیز القا می‌کند مگر بعداً override شود.

</details>

## 104.5 — مجوز و مالکیت؛ چرا Permission denied می‌بینیم؟

### مفهوم و کاربرد

سه دسته دسترسی داریم: مالک، گروه و دیگران. r=4 خواندن، w=2 نوشتن و x=1 اجرا/عبور است. فایل با x قابل اجرای مستقیم می‌شود؛ پوشه با x قابل پیمایش است. برای حذف فایل معمولاً مجوز نوشتن و عبور در پوشهٔ والد مهم است، نه w خود فایل. sticky محدودیت دیگری می‌افزاید.

`chmod` دسترسی، `chown` مالک و `chgrp` گروه مالک را تغییر می‌دهد. UID عدد هویت کاربر و GID عدد گروه است. فایل می‌تواند mode درست داشته باشد ولی ACL، SELinux/AppArmor یا مسیر والد دسترسی را محدود کند؛ chmod 777 پاسخ عمومی نیست.

### مثال 1: خواندن و تغییر mode

بدون sudo و فقط فایل تمرین.

```bash
perm_lab=$(mktemp -d)
cd "$perm_lab"
printf 'private
' > note.txt
chmod 640 note.txt
ls -l note.txt
chmod u+x,g-r note.txt
```

**توضیح خط‌به‌خط:**

1. پوشهٔ خصوصی تازه می‌سازد.
2. وارد آن می‌شویم.
3. فایل داده می‌سازد.
4. مالک 6=rw، گروه 4=r و دیگران 0؛ این فایل executable نیست.
5. باید -rw-r----- و نام مالک/گروه را ببینید.
6. فقط x مالک اضافه و r گروه حذف می‌شود؛ محتوا به script معتبر تبدیل نمی‌شود.

**نتیجه و بررسی:** پس از خط آخر mode برابر 700 است. بیت execute کافی نیست؛ قالب برنامه و interpreter هم مهم‌اند.

### مثال 2: umask در محیط محدود

در همان پوشه؛ پرانتز یک subshell می‌سازد تا umask والد تغییر نکند.

```bash
(
umask 027
touch fresh-file
mkdir fresh-dir
stat -c "%a %n" fresh-file fresh-dir
)
```

**توضیح خط‌به‌خط:**

1. شروع subshell؛ خط‌های بعد در محیط فرزندند.
2. ماسک بیت‌های گروه/دیگران برای فایل‌های جدید تنظیم می‌شود.
3. فایل تازه معمولاً با درخواست 666 ساخته می‌شود؛ نتیجه 640.
4. پوشه تازه معمولاً با درخواست 777 ساخته می‌شود؛ نتیجه 750.
5. a عدد mode و n نام فایل را می‌دهد.
6. خروج از subshell؛ umask shell اصلی حفظ می‌شود.

**نتیجه و بررسی:** روی فایل‌سیستم معمول بدون ACL ارثی، 640 و 750 می‌بینید. umask فایل موجود را تغییر نمی‌دهد و تفریق ده‌دهی نیست.

### مثال 3: بیت‌های ویژه در پوشه

فقط پوشه‌های آزمایش متعلق به خودتان.

```bash
mkdir team shared
chmod 2770 team
chmod 1777 shared
ls -ld team shared
```

**توضیح خط‌به‌خط:**

1. دو پوشهٔ تازه می‌سازیم.
2. 2 بیت SGID و 770 دسترسی کامل مالک و گروه؛ فایل جدید گروه این پوشه را به ارث می‌برد.
3. 1 sticky و 777 دسترسی عمومی؛ حذف نام دیگران به مالک فایل، مالک پوشه یا دارندهٔ مجوز ویژه محدود می‌شود.
4. d خود پوشه را نشان می‌دهد، نه محتویات؛ s/t را در mode می‌بینید.

**نتیجه و بررسی:** والد mktemp خصوصی است، پس این نمونه هنوز پوشهٔ واقعاً مشترک بین کاربران نیست. آزمون دوکاربره در آزمایشگاه تکمیلی آمده است.

### اشتباه رایج و عیب‌یابی

برای دیدن مجوز پوشه ls -ld لازم است. S یا T بزرگ یعنی بیت ویژه هست ولی x در همان محل نیست. افزودن SUID روی script Bash راه درست افزایش دسترسی نیست.

### نکته‌های تکمیلی این سرفصل

`sudo chown alice:ops FILE` مالک و گروه را به حساب/گروه موجود تغییر می‌دهد؛ `chgrp ops FILE` فقط گروه است و کاربر عادی معمولاً باید عضو آن باشد. `chmod u+s PROGRAM` در executable مناسب effective UID را به مالک برنامه می‌دهد؛ نیاز به بررسی امنیتی دارد. روی لینک نمادین chmod معمولاً هدف را تغییر می‌دهد. ACL پیش‌فرض پوشه می‌تواند نتیجهٔ ساخت را متفاوت از جدول سادهٔ umask کند.

### تمرین مستقل

2750 را به زبان ساده توضیح دهید؛ آیا دیگران می‌توانند پوشه را پیمایش کنند؟

<summary>پاسخ تشریحی؛ ابتدا خودتان حل کنید</summary>

SGID فعال، مالک rwx، گروه r-x و دیگران هیچ دسترسی ندارند. دیگران نمی‌توانند پیمایش کنند، مگر مجوز دیگری مثل ACL یا امتیاز مدیریتی داشته باشند.

## 104.6 — Hard link و Symbolic link

### مفهوم و کاربرد

Hard link نام دیگری برای همان inode در همان فایل‌سیستم است. کپی inode و دادهٔ مستقل دارد. symlink فایل جداگانه‌ای است که مسیر مقصد را نگه می‌دارد. اگر مقصد symlink پاک شود لینک می‌شکند؛ hard link دیگر همچنان داده را نگه می‌دارد. hard link به پوشه در کار عادی ممنوع و عبور از مرز filesystem برایش ممکن نیست.

### مثال 1: ساخت سه نوع مرجع

محیط تازه.

```bash
link_lab=$(mktemp -d)
cd "$link_lab"
printf 'one
' > original
ln original hard
ln -s original soft
cp original copy
ls -li original hard soft copy
```

**توضیح خط‌به‌خط:**

1. پوشهٔ یکتا ایجاد می‌کند.
2. وارد آن می‌شود.
3. فایل اولیه می‌سازد.
4. نام hard را برای همان inode می‌سازد؛ اول هدف، بعد نام جدید.
5. s لینک نمادین ایجاد می‌کند که متن original را نگه می‌دارد.
6. نسخهٔ مستقل می‌سازد.
7. i inode و l جزئیات و link count را می‌دهد.

**نتیجه و بررسی:** original و hard inode برابر و link count=2 دارند؛ soft و copy inode جدا دارند.

### مثال 2: ویرایش و حذف نام اصلی

در همان پوشه؛ تنها دادهٔ آزمایش.

```bash
printf 'two
' >> hard
cat original soft copy
rm -i original
cat hard
ls -l soft
```

**توضیح خط‌به‌خط:**

1. از نام hard به همان داده خطی اضافه می‌کند.
2. دو نام اول one و two، اما کپی تنها one دارد.
3. پس از خواندن مسیر و تأیید، یکی از نام‌ها حذف می‌شود.
4. داده همچنان one و two است.
5. لینک هنوز وجود دارد ولی به نام حذف‌شده اشاره می‌کند.

**نتیجه و بررسی:** `cat soft` خطای نبود مقصد می‌دهد. حذف نام symlink خودش دادهٔ هدف را حذف نمی‌کند.

### مثال 3: لینک نسبی

در همان پوشه.

```bash
mkdir releases
printf 'v1
' > releases/version
ln -s releases/version current
readlink current
cat current
```

**توضیح خط‌به‌خط:**

1. پوشهٔ هدف جدید می‌سازد.
2. دادهٔ نسخه می‌نویسد.
3. مسیر نسبی releases/version را داخل لینک ذخیره می‌کند.
4. متن مقصد لینک را می‌خواند، نه محتویات فایل مقصد.
5. مسیر نسبت به پوشهٔ حاوی لینک حل می‌شود و v1 چاپ می‌کند.

**نتیجه و بررسی:** اگر current را به پوشهٔ دیگری منتقل کنید همان متن نسبی ممکن است دیگر درست حل نشود.

### اشتباه رایج و عیب‌یابی

نام hard-backup به hard link ماهیت backup نمی‌دهد؛ ویرایش یکی در دیگری دیده می‌شود. عدد inode فقط درون یک filesystem شناسهٔ قابل مقایسه است.

### تمرین مستقل

بعد از حذف original چه چیزی باعث ماندن داده می‌شود و کی فضا آزاد می‌شود؟

## 104.7 — نقشهٔ پوشه‌ها و پیداکردن فایل

### مفهوم و کاربرد

FHS قرارداد محل قرارگرفتن فایل‌هاست. `/etc` تنظیم دستگاه، `/var` دادهٔ متغیر، `/usr` برنامه و دادهٔ اشتراکی، `/usr/local` نصب محلی مدیر، `/opt` نرم‌افزار افزوده، `/srv` دادهٔ خدمت‌رسانی، `/home` خانهٔ کاربران، `/root` خانهٔ root، `/run` وضعیت از زمان boot و `/tmp` فایل موقت است. `/` ریشهٔ درخت است، نه خانهٔ root.

در نصب merged-usr، bin/sbin/lib در ریشه ممکن است پیوند به usr باشند؛ این به‌معنی حذف مفهوم آن‌ها نیست. /usr محل معمول فایل شخصی کاربر نیست.

### مثال 1: دیدن ساختار

فقط خواندن.

```bash
ls -ld / /root /home /etc /var /usr /run
ls -ld /bin /sbin /lib
readlink -f /bin
```

**توضیح خط‌به‌خط:**

1. d ویژگی خود پوشه‌ها را نشان می‌دهد؛ حق دیدن metadata با خواندن محتویات یکسان نیست.
2. اگر symlink باشند فلش مقصد را می‌بینید.
3. مسیر نهایی واقعی را دنبال می‌کند؛ در merged-usr معمولاً /usr/bin است.

**نتیجه و بررسی:** نباید مسیر توزیع خود را صرفاً برای شبیه‌شدن به کتاب جابه‌جا کنید.

### مثال 2: پیداکردن برنامه

همهٔ ابزارها یک کار نمی‌کنند.

```bash
type -a passwd
command -v passwd
whereis passwd
find /usr/share/man -type f -name 'passwd*'
```

**توضیح خط‌به‌خط:**

1. تشخیص shell از نام دستور را می‌دهد.
2. مسیر/نوع قابل اجرای دستور از نگاه shell را می‌دهد.
3. مسیرهای رایج executable، source و manual را جست‌وجو می‌کند.
4. فایل‌های راهنمای دارای نام passwd را از درخت زنده پیدا می‌کند.

**نتیجه و بررسی:** نبود man در نصب minimal ممکن است باعث نتیجهٔ خالی شود. find پوشه را می‌گردد ولی type قوانین shell را می‌سنجد.

### مثال 3: جست‌وجوی database

locate ممکن است از بستهٔ plocate یا mlocate باشد؛ نصب آن اختیاری برای این تمرین است.

```bash
locate passwd
locate -e passwd
cat /etc/updatedb.conf
```

**توضیح خط‌به‌خط:**

1. نام‌های حاوی passwd را از پایگاه آماده جست‌وجو می‌کند.
2. در پیاده‌سازی پشتیبان، e وجود فعلی نتیجه‌ها را نیز بررسی می‌کند.
3. تنظیم مسیرها/فایل‌سیستم‌های کنارگذاشته‌شده را می‌خواند، اگر این پیاده‌سازی فایل را دارد.

**نتیجه و بررسی:** فایل تازه ممکن است در پایگاه نباشد؛ `sudo updatedb` آن را تازه می‌کند ولی پیمایش گسترده ممکن است زمان ببرد. برای یک فایل تازه find بهتر است.

### اشتباه رایج و عیب‌یابی

خطای Permission denied در find به معنی نبود هیچ نتیجه نیست؛ یک زیرشاخه قابل خواندن نبوده است. برای گزارش کامل دامنهٔ دسترسی را مشخص کنید.

### تمرین مستقل

تنظیم سرویس، log و script نصب محلی مدیر را به چه مسیرهایی می‌برید؟
