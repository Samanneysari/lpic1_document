## 109.1 Internet protocol fundamentals

### What this objective teaches

Understand addresses, prefixes, routes, TCP, UDP, ICMP, IPv4, IPv6, and required ports.

### Worked example 1: Read assigned addresses

```bash
ip -brief address
```

**Line-by-line explanation:**

1. `ip address` reads interface addresses; `-brief` produces one compact row per interface.

**What to verify:** IPv4 uses dotted decimal, while IPv6 uses colon-separated hexadecimal.

### Worked example 2: Look up a service port

```bash
getent services ssh
```

**Line-by-line explanation:**

1. `getent services` follows the system service database and asks for the entry named `ssh`.

**What to verify:** The normal mapping is TCP port 22.

### Worked example 3: Inspect routes

```bash
ip route show
```

**Line-by-line explanation:**

1. `ip route show` prints the IPv4 routing table without changing it.

**What to verify:** A line beginning with `default via` names the usual gateway.

### Common mistakes and troubleshooting

Do not copy a device name, account name, service name, or path without checking that it exists on your machine. A command that prints nothing may have found no matches; check its exit status with `printf 'status=%s\n' "$?"`. Read permission errors instead of hiding them, and use `man COMMAND` before adding an unfamiliar write or delete option.

## 109.2 Persistent network configuration

### What this objective teaches

Configure host identity, name lookup, NetworkManager, and distribution network files persistently.

### Worked example 1: Read the static host name

```bash
hostnamectl --static
```

**Line-by-line explanation:**

1. `hostnamectl --static` asks systemd-hostnamed for the configured static host name.

**What to verify:** This can differ from a temporary or transient name.

### Worked example 2: List NetworkManager profiles

```bash
nmcli connection show
```

**Line-by-line explanation:**

1. `nmcli connection show` lists saved NetworkManager connection profiles and their current device association.

**What to verify:** A profile is persistent configuration; it is not the same thing as an interface.

### Worked example 3: Read lookup order

```bash
grep '^hosts:' /etc/nsswitch.conf
```

**Line-by-line explanation:**

1. `grep` selects the `hosts:` database line that defines sources and order for name resolution.

**What to verify:** Common sources include `files`, `dns`, and systemd-related modules.

### Common mistakes and troubleshooting

Do not copy a device name, account name, service name, or path without checking that it exists on your machine. A command that prints nothing may have found no matches; check its exit status with `printf 'status=%s\n' "$?"`. Read permission errors instead of hiding them, and use `man COMMAND` before adding an unfamiliar write or delete option.

## 109.3 Network troubleshooting

### What this objective teaches

Troubleshoot from link and address through route, DNS, transport, and application layers.

### Worked example 1: Check link state

```bash
ip -brief link
```

**Line-by-line explanation:**

1. `ip link` reads interfaces; `-brief` makes state, name, and link-layer address easy to scan.

**What to verify:** `UP` is administrative state; `LOWER_UP` usually means the link is detected.

### Worked example 2: Check a route decision

```bash
ip route get 1.1.1.1
```

**Line-by-line explanation:**

1. `ip route get` asks the kernel how it would reach the destination without sending a packet.

**What to verify:** The result identifies route, gateway, source address, and output interface.

### Worked example 3: List listening sockets

```bash
ss -lntup
```

**Line-by-line explanation:**

1. `ss` reads sockets; `-l` keeps listeners, `-n` avoids name lookup, `-t` and `-u` include TCP and UDP, and `-p` requests process data.

**What to verify:** Some process names require root privileges.

### Common mistakes and troubleshooting

Do not copy a device name, account name, service name, or path without checking that it exists on your machine. A command that prints nothing may have found no matches; check its exit status with `printf 'status=%s\n' "$?"`. Read permission errors instead of hiding them, and use `man COMMAND` before adding an unfamiliar write or delete option.

## 109.4 Client-side DNS

### What this objective teaches

Follow local name resolution from NSS and hosts files to configured DNS servers.

### Worked example 1: Use the application lookup path

```bash
getent ahosts example.com
```

**Line-by-line explanation:**

1. `getent ahosts` uses the configured NSS path, similar to many applications, and requests addresses for the name.

**What to verify:** Results can come from `/etc/hosts`, DNS, or another configured source.

### Worked example 2: Ask DNS directly

```bash
dig example.com A +short
```

**Line-by-line explanation:**

1. `dig` sends a DNS query for IPv4 A records; `+short` keeps only the concise answer data.

**What to verify:** One or more IPv4 addresses normally appear.

### Worked example 3: Inspect resolver state

```bash
resolvectl status
```

**Line-by-line explanation:**

1. `resolvectl status` shows global and per-link DNS servers, search domains, and protocols on systemd-resolved systems.

**What to verify:** If resolved is not in use, inspect `/etc/resolv.conf` and the active network manager instead.

### Common mistakes and troubleshooting

Do not copy a device name, account name, service name, or path without checking that it exists on your machine. A command that prints nothing may have found no matches; check its exit status with `printf 'status=%s\n' "$?"`. Read permission errors instead of hiding them, and use `man COMMAND` before adding an unfamiliar write or delete option.
